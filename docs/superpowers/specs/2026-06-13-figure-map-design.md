# CrickNote Spec: Figure Map for CREATE Reading Notes

**Date:** 2026-06-13
**Status:** Draft
**Scope:** Add a Figure Map section to reading notes — a table at the top that maps each paper figure to what it shows and which conclusion it proves or challenges, drafted by the LLM during compile and corrected by the user.
**Depends on:** Spec 2 — Knowledge Base Workflow (CREATE framework, compile step)
**Does NOT touch:** KB pipeline (`kb_suggest`, `kb_apply`), DB schema, reading note frontmatter

---

## 1. Problem

When revisiting a paper note weeks or months later, the CREATE sections require re-reading to reconstruct which experiment proved which conclusion. There is no quick-reference view of the paper's evidence structure. The user has to re-read the Evidence and Reasoning sections to remember what Fig 2 actually showed or why Fig 3B matters.

---

## 2. Solution

Add a `## Figure Map` section at the top of each reading note — before the CREATE sections — containing a 3-column markdown table:

| Figure | What it shows | Significance |
|--------|--------------|--------------|
| Fig 1A | IL-42 binds CD8 receptor (ELISA dose-response) | Proves the binding mechanism — the premise for all suppression claims |
| Fig 2 | 40% CD8 suppression in Jurkat cells (flow cytometry) | Headline result; establishes magnitude of the effect |
| Fig 3B | Only 12% suppression in primary T cells | Challenges the headline result — authors attribute to receptor density differences |
| Fig 4 | Blocking antibody rules out direct contact model | Rules out the competing mechanism proposed in the Introduction |
| Suppl. S2 | Effect absent at <5 nM IL-42 | Establishes concentration threshold not discussed in the main text |

**Column definitions:**

- **Figure** — the panel label as it appears in the paper (Fig 1, Fig 2A, Table 2, Suppl. S1, etc.). Include supplementary figures when described in the compiled text.
- **What it shows** — one factual sentence: what experiment was done and what data it produced.
- **Significance** — which conclusion of this paper this figure establishes or challenges, drawn from the paper's own abstract, results, and discussion. No cross-paper comparisons unless the paper explicitly makes them. One sentence.

**Generation:** The LLM drafts the Figure Map during the compile step, using only the compiled source text. Where figure caption text is unclear or missing from the extraction, the LLM leaves the cell as `?`. The user corrects the draft before marking `status: complete`.

**Honest expectation:** For well-formatted PDFs with NotebookLM summaries, the draft will be mostly accurate. For scanned or older PDFs where captions are embedded in images, many cells may be `?` and the user fills them manually. This is expected behaviour, not a failure.

---

## 3. Placement

`## Figure Map` appears at the top of the note body, before `## Claims`. This gives it "TL;DR" function — a reader revisiting the note sees the evidence structure immediately without scrolling through the CREATE sections.

Full note structure after this change:

```markdown
---
frontmatter
---

# {Title}

## Figure Map

| Figure | What it shows | Significance |
|--------|--------------|--------------|
| ...    | ...          | ...          |

## Claims
## Reasoning
## Evidence
## Assumptions
## Takeaways
## Extensions
```

---

## 4. Empty Scaffold

The empty scaffold (generated by `buildCreateReadingBody` when creating a new reading note) includes only the `## Figure Map` heading with no table rows — matching the pattern of the CREATE sections (which are also headings with no content).

```markdown
## Figure Map

## Claims

## Reasoning
...
```

This is required so that `hasMeaningfulReadingBody` correctly returns `false` for a new uncompiled note. If table header rows were included in the scaffold, the section would contain non-empty content and the pipeline would incorrectly skip the compile step.

---

## 5. Compile Step Instructions (Skill)

The LLM receives these instructions when drafting the compile output:

1. Scan the compiled text for all figure, table, and supplementary panel references.
2. For each reference found, generate one row:
   - **Figure**: use the exact label as it appears in the paper
   - **What it shows**: one factual sentence describing the experiment and data
   - **Significance**: one sentence tracing this figure to the conclusion it proves or challenges — using only what the paper's own abstract, results, and discussion say. If the paper does not explain why a figure matters, write `?`
   - Mark any cell `?` where the text was too unclear to fill accurately
3. Order rows by label number (Fig 1, Fig 2, Fig 3... then Suppl. S1, Suppl. S2...). Main figures first, supplementary panels at the end. Where panel labels are ambiguous (e.g. Fig 2A and Fig 2B are separate experiments), use one row per panel.
4. Present the Figure Map draft above the CREATE section drafts so the user reviews both together.
5. **If no figures are found** (review papers, theory papers, methods papers): leave the `## Figure Map` section with a single comment line: `<!-- No data figures found in compiled sources -->`. Do not generate an empty table. The user may fill it manually or leave it.

---

## 6. Pipeline Integration

The Figure Map is a reading aid. The KB pipeline is untouched.

- `kb_suggest` reads the CREATE sections as before and ignores the Figure Map
- `kb_apply` is unchanged
- `kb_status`, `kb_lint`, mapping artifacts — all unchanged
- `inferReadingPipelineStep` is unchanged — Figure Map content (when present) counts as meaningful body content, and the existing `hasMeaningfulReadingBody` check works correctly

## 7. What Changes

### `src/knowledge/reading-note.ts`

**Add constant:**
```ts
export const FIGURE_MAP_HEADING = 'Figure Map' as const;
```

**Update `buildCreateReadingBody`:**
```ts
export function buildCreateReadingBody(meta: Pick<ReadingNoteMeta, 'title'>): string {
  const figureMapSection = `## ${FIGURE_MAP_HEADING}\n`;
  const sections = CREATE_SECTION_HEADINGS.map((heading) => `## ${heading}\n`).join('\n');
  return `\n# ${meta.title}\n\n${figureMapSection}\n${sections}`;
}
```

**Add function:**
```ts
export function hasFigureMapHeading(body: string): boolean {
  return new RegExp(`^## ${FIGURE_MAP_HEADING}\\s*$`, 'm').test(body);
}
```

### `skills/cricknote-reading-intake/SKILL.md`

Update the "Analyze the paper" step to include Figure Map drafting instructions (see §5).

## 9. Design Decisions and Rationale

**Why drop the Role column (supports/caveat/contradicts)?**
A one-emoji status badge carries no context. Replaced by the Significance column which explains *why* a figure matters instead of labelling it.

**Why drop the Claim column?**
Creates silent staleness: if the user restructures the Claims section, all Claim references in the Figure Map silently become wrong. No enforcement mechanism. Dropped in favour of robustness. Can be added later if Approach 2 (KB-integrated figure map) is built.

**Why restrict Significance to intra-paper only?**
The LLM only has the current paper's compiled text during the compile step. Cross-paper comparisons would require the LLM to draw on training data, producing unreliable or hallucinated comparisons. Restricting to what the paper itself says keeps the column accurate and trustworthy.

**Why no table rows in the empty scaffold?**
Table header rows contain non-empty text. Including them in the empty scaffold would cause `hasMeaningfulReadingBody` to return `true` for an uncompiled note, incorrectly skipping the compile step in `inferReadingPipelineStep`.

**Why not add Figure Map to `CREATE_SECTION_HEADINGS`?**
CREATE is a specific acronym framework. Figure Map is a separate structural aid, not a CREATE section. Keeping them distinct avoids polluting the `CREATE_SECTION_HEADINGS` constant used by `hasCreateHeadings` and `kb_suggest`.
